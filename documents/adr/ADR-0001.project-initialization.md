# ADR-0001: ساختار مستندات معماری پروژه

* **وضعیت**: پیشنهادی
* **تاریخ**: ۲۰۲۵/۱۲/۱۱
* **تصمیم گیرندگان**: تیم معماری پروژه trade-loan

## زمینه و متن (Context)

با توجه به پیچیدگی پروژه trade-loan و نیاز به مستندسازی جامع معماری، تیم به یک ساختار منسجم برای مستندات معماری نیاز داشت. پروژه شامل میکروسرویس‌های متعدد با روابط پیچیده و استانداردهای بالای کیفیت کد است.

نیازهای اصلی شامل موارد زیر بود:
- مستندسازی تصمیمات معماری به زبان فارسی
- نگهداری نمودارهای C4 برای نمایش معماری سیستم
- مستندسازی API ها با استفاده از OpenAPI
- مستندسازی پیام‌رسانی نامتقارن با AsyncAPI
- مستندسازی مدل‌های دامنه و پایگاه داده
- نمایش روابط بین بومی‌های دامنه (Context Mapping)

## تصمیم (Decision)

ایجاد ساختار جامع مستندات معماری در مسیر `/documents/` با شش بخش اصلی:

1. **C4 Model** (`c4/`): نمودارهای معماری در چهار سطح مختلف
2. **Architecture Decision Records** (`adr/`): ثبت تصمیمات معماری
3. **Context Mapping** (`cmap/`): نمایش روابط بین بومی‌های دامنه
4. **OpenAPI** (`openapi/`): مستندسازی API های REST
5. **AsyncAPI** (`asyncapi/`): مستندسازی پیام‌رسانی نامتقارن
6. **Data Models** (`datamodels/`): مستندسازی مدل‌های داده و پایگاه داده

هر بخش شامل فایل README.md با راهنمای کامل و الگوهای استاندارد است.

## دلایل و نتایج (Consequences)

### مزایا (Pros)

- **یکپارچگی مستندات**: تمام مستندات معماری در یک مکان متمرکز
- **استانداردسازی**: استفاده از فرمت‌های استاندارد صنعتی (MADR، OpenAPI، AsyncAPI، C4)
- **زبان محلی**: مستندات به زبان فارسی برای درک بهتر تیم
- **نگهداری آسان**: ساختار واضح برای به‌روزرسانی مداوم
- **تکامل تدریجی**: امکان شروع با مستندات اولیه و تکامل آن‌ها
- **همکاری تیمی**: ساختار مناسب برای کار گروهی و بازبینی

### معایب (Cons)

- **نیاز به یادگیری**: تیم باید با فرمت‌های جدید آشنا شود
- **زمان اولیه**: ایجاد ساختار اولیه نیازمند زمان است
- **نگهداری مستمر**: نیاز به به‌روزرسانی منظم مستندات
- **پیچیدگی**: ساختار جامع ممکن است در ابتدا پیچیده به نظر برسد

### نتایج مورد انتظار

- **افزایش شفافیت**: درک بهتر معماری سیستم برای همه اعضای تیم
- **کاهش وابستگی**: دانش معماری فقط به افراد خاص محدود نمی‌شود
- **بهبود کیفیت**: مستندات جامع به طراحی‌های بهتر کمک می‌کند
- **تسهیل آنبوردینگ**: اعضای جدید سریع‌تر با معماری آشنا می‌شوند

## جایگزین‌های بررسی شده (Alternatives Considered)

### ۱. استفاده فقط از Confluence
**مزایا**: دسترسی آسان، قابلیت جستجوی خوب، ادیت همزمان
**معایب**: وابستگی به ابزار خارجی، کنترل نسخه ضعیف، دشواری در ادیت کد
**نتیجه**: رد شد چون کنترل نسخه و ادیت کد مهم است

### ۲. مستندات پراکنده در خود کد
**مزایا**: نزدیکی به کد، به‌روزرسانی همزمان
**معایب**: عدم وجود دید کلی، جستجوی دشوار، ساختار نامنظم
**نتیجه**: رد شد چون دید جامع معماری را فراهم نمی‌کند

### ۳. استفاده از ابزارهای تخصصی معماری (مثل Structurizr)
**مزایا**: ابزارهای پیشرفته برای معماری
**معایب**: هزینه، نیاز به یادگیری ابزار جدید، وابستگی به vendor
**نتیجه**: رد شد چون پیچیدگی را افزایش می‌دهد

### ۴. ساختار ساده فقط برای ADRها
**مزایا**: شروع آسان، پیچیدگی کم
**معایب**: ناکامل بودن، پوشش ندادن جنبه‌های دیگر معماری
**نتیجه**: رد شد چون جامع نیست

## پیاده‌سازی

### گام‌های اجرایی

1. **ایجاد ساختار دایرکتوری**
   ```bash
   mkdir -p documents/{c4,adr,cmap,openapi,asyncapi,datamodels}
   ```

2. **ایجاد فایل‌های README**
   - هر بخش یک README.md با راهنمای کامل
   - شامل استانداردها، ابزارها، و بهترین شیوه‌ها

3. **ایجاد اولین ADR**
   - مستندسازی خود این تصمیم به عنوان ADR-0001
   - استفاده از فرمت MADR فارسی

4. **آموزش تیم**
   - معرفی فرمت‌های جدید به تیم
   - ایجاد دستورالعمل‌های نگهداری مستندات

### ابزارهای پیشنهادی

- **ویرایش**: VS Code با پلاگین‌های Markdown و PlantUML
- **نمودارها**: PlantUML برای C4 و Context Mapping
- **API**: Swagger/OpenAPI برای مستندسازی REST API
- **مessaging**: AsyncAPI برای مستندسازی پیام‌رسانی
- **نسخه**: Git برای کنترل نسخه مستندات

### اندازه‌گیری موفقیت

- **پوشش مستندات**: تمام جنبه‌های معماری مستند شوند
- **به‌روزرسانی**: مستندات همزمان با تغییرات کد به‌روز شوند
- **استفاده**: تیم به طور منظم از مستندات استفاده کند
- **بازخورد**: دریافت بازخورد منظم از تیم برای بهبود
