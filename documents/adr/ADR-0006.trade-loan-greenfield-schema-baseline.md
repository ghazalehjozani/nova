# ADR-0006. baselineِ greenfieldِ schema برای trade-loan + UUID v7 + سیاستِ runnerِ مهاجرت

- **وضعیت:** پذیرفته شده
- **تاریخ:** 2026-06-18
- **نویسندگان:** مهدی امیرعبدالهی
- **اسناد تحت تأثیر:** ADR-0004 (قراردادِ قفلِ خوش‌بینانه — نوعِ ستونِ `version`)

## زمینه و شرح مسئله

changelogهای trade-loan طیِ زمان به انباشتی از مهاجرت‌های add-column / alter / repoint / retype و فایل‌های نسخه‌ایِ تکراری تبدیل شده بودند که برخی به مسیرهای حذف‌شدهٔ pangaea ارجاع می‌دادند و برخی (drop/cleanupهای مربوط به saga) روی دیتابیسِ خالی شکست می‌خوردند. با مهاجرت به PostgreSQL 18 و Spring Boot 4.1، schema را به‌صورتِ greenfield بازنویسی کردیم تا دقیقاً وضعیتِ نهاییِ فعلی را که entityهای `adapters/driven/persistence` با `validate` می‌سنجند، بازتاب دهد.

این ADR تصمیمِ سمتِ nova را ثبت می‌کند؛ کنوانسیون‌های زیربناییِ پلتفرم در pangaea ADR-0028 (تنظیم PG18)، ADR-0029 (UUID v7)، ADR-0030 (قالبِ changelog)، و ADR-0031 (Liquibase 5.0.3) کدگذاری شده‌اند و اینجا فقط به آن‌ها ارجاع می‌دهیم.

## محرک‌های تصمیم‌گیری

- bootstrapِ صحیحِ دیتابیسِ تازه: master روی DB خالی باید به وضعیتِ نهایی برسد، بدونِ هیچ changesetی که فرض می‌کند چیزی از قبل هست.
- هم‌راستایی با استانداردِ پلتفرم: کلیدِ اصلیِ UUID v7، نوعِ `version integer`، تنظیمِ PG18، قالبِ changelogِ formatted-SQL.
- ترکیبِ صحیحِ framework + دامنه: جدول‌های زیرساختیِ pangaea/expression-kit باید پیش از جدول‌های دامنهٔ trade-loan ساخته شوند.
- سیاستِ migrationِ ایمن برای ناوگانِ چندنمونه‌ای (rolling deploy).

## گزینه‌های بررسی‌شده

- **گزینهٔ ۱ — پورتِ changelogهای تاریخی همان‌طور که بودند.** رد شد: driftِ تاریخی + changesetهای drop/cleanupِ saga روی DB خالی می‌شکنند یا بی‌معنا هستند.
- **گزینهٔ ۲ (انتخاب‌شده) — baselineِ greenfield از وضعیتِ نهایی + ترکیبِ صریحِ masterهای ماژولیِ pangaea/expression-kit + UUID v7 + سیاستِ runnerِ مهاجرت.**

## نتیجه تصمیم

گزینهٔ انتخابی: «گزینهٔ ۲». master فقط include دارد و ترتیبش «framework اول، بعد trade-loan» است؛ هر برگ یک changesetِ formatted-SQL است که وضعیتِ نهایی را می‌سازد.

### masterِ نازک، ترتیبِ framework → دامنه

masterِ بالایی فقط دو خط include دارد (framework، سپس trade-loan). masterِ framework هر شش masterِ ماژولیِ pangaea/expression-kit را که به‌صورتِ منبعِ ریشهٔ‌classpath درونِ jarِ هر وابستگی ship می‌شوند، با includeِ صریح و مرتب (persistence → inbox → audit → reconciliation → workflow → expression-kit) می‌آورد — `relativeToChangelogFile` ندارد چون این‌ها منابعِ بین‌jar هستند که از ریشهٔ classpath resolve می‌شوند. هیچ‌جا `includeAll` نیست. masterِ trade-loan برگ‌های دامنه را به ترتیبِ چرخهٔ حیات می‌آورد: داده‌های مرجع → application → schedule → sanction → facility → installment-schedule → چهار جدولِ outbox.

### folding driftِ تاریخی + حذفِ saga

همهٔ مهاجرت‌های add-column/alter/repoint/retypeِ تاریخی درونِ create-leafِ همان جدول folded شدند (مثلاً ستون‌های actor-envelope + traceparent/tracestate در هر outbox؛ ستون‌های close-paid-off/cancellation در `loan_facilities`؛ end-stateِ base-loan 6.8 برای disbursement/restructuring/sanctioned). جدول‌های بازنشسته‌شدهٔ `saga_*` (saga→workflow، LN-59501) اصلاً ساخته نمی‌شوند، پس هیچ changesetِ drop/delete وجود ندارد. کامنتِ masterِ trade-loan این را صریح ثبت کرده است.

### UUID v7 + `DEFAULT uuidv7()` + `version integer`

هر کلیدِ اصلی `id uuid NOT NULL DEFAULT uuidv7()` است (اپ شناسه را با `Identity.generateV7()` می‌گذارد؛ `DEFAULT` شبکهٔ ایمنی است — pangaea ADR-0029). ستونِ قفلِ خوش‌بینانه `version integer` است (هم‌راستا با ADR-0004 و تغییرِ `Long`→`Integer` در موجودیتِ پایهٔ pangaea). نمونهٔ یک برگِ outbox (تنظیمِ PG18 طبقِ ADR-0028 — چیدمانِ ستونِ نزولی، `fillfactor`، lz4، autovacuum، ایندکسِ dispatchِ partial، BRIN روی `created_at`):

### سیاستِ runnerِ مهاجرت (dev در برابر stage/prod)

- **dev/test:** Liquibase درونِ اپ روی boot (`spring.liquibase.enabled=true` در nova-config). برای محیطِ تک‌نمونه بی‌خطر.
- **stage/prod:** اپ‌ها هرگز migrate نمی‌کنند (`spring.liquibase.enabled=false`)؛ یک runnerِ اختصاصی **پیش از** rolling کردنِ podهای اپ مهاجرت را اجرا می‌کند تا N نمونهٔ اپ هرگز روی `DATABASECHANGELOGLOCK` رقابت نکنند. مسیرهای operator: `make db-*` / `mvn -pl container -Pliquibase-ops liquibase:<goal>` / کانتینرِ `liquibase/liquibase:5.0.3`. الگوی `tag` per release برای rollback و expand/contract برای rolling deployهای آینده. جزئیاتِ کاملِ عملیاتی در **RB-0004** است.

### پیامدهای مثبت

- bootstrapِ دیتابیسِ تازه قطعی و صحیح (هیچ drop/delete روی DB خالی).
- هم‌راستا با استانداردِ پلتفرم: UUID v7، `version integer`، تنظیمِ PG18، قالبِ changelog.
- migrationِ ناوگانِ تولیدی ایمن (runnerِ یگانه، بدونِ رقابتِ قفل).

### پیامدهای منفی

- baselineِ greenfield تاریخِ migrationِ گذشته را بازتولید نمی‌کند؛ مناسبِ استقرارِ تازه است، نه apply مستقیم روی یک دیتابیسِ موجودِ تولیدی.
- انضباطِ دستی: هر برگِ جدید باید با includeِ صریح به masterِ متناظر اضافه شود؛ فایلِ یتیم در زمانِ اجرا `column does not exist` می‌دهد.
